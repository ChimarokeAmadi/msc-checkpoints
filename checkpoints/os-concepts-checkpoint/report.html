1.1 First Come, First Served (FCFS)

The CPU runs the processes in the order they arrive, and each one runs until it finishes (non-preemptive). P1 arrives first at time 0 and keeps the CPU until time 5, even though P2 and P3 arrive while it's running. Then P2 runs from 5 to 8, and P3 from 8 to 9.

1.3 Which algorithm is more responsive?

Here the average waiting time is the same for both algorithms (3.33), but the waiting is shared very differently. With FCFS, the short process P3 (only 1 unit of work) waits 6 units because it's stuck behind the long P1. This is called the convoy effect. With Round Robin, P3 waits only 2 units, and nobody waits more than 4.

Round Robin is more responsive. Responsiveness is about how soon a process first gets the CPU (response time), and the average response time drops from 3.33 with FCFS to 1 with Round Robin. Every process is guaranteed a turn within a short, bounded time, at most (n − 1) × quantum, because the CPU is preempted after each quantum. That's why time-sharing and interactive systems use Round Robin-style scheduling. The cost is extra context switches (5 switches instead of 2 here), and turnaround time doesn't improve (6.33 for both). If the quantum is too large, Round Robin behaves like FCFS. If it's too small, most of the time is spent switching.

With the other convention (the preempted P1 queued before the newly arrived P3), the order would be P1, P2, P1, P3, P2, P1 and the average waiting time would be 4.00. Round Robin would still have the better response time.

Part 2: Process Synchronization

P1 and P2 share the variable counter (starting at 0), and each increments it 100 times. The expected final value is 200.

2.1 What could go wrong without synchronization

The problem is a race condition. counter = counter + 1 looks like one step, but the CPU actually does it in three: LOAD the value into a register, ADD 1, and STORE it back. The scheduler can switch between P1 and P2 in the middle of these steps. If both load the same value before either stores, one of the increments is lost:

StepProcessInstructionIts registercounter in memory
1P1LOAD counter → reg00
2P2LOAD counter → reg00
3P1ADD reg + 110
4P2ADD reg + 110
5P1STORE reg → counter11
6P2STORE reg → counter11

Two increments happened, but counter only went from 0 to 1. Because this can happen any number of times, the final result is unpredictable and is usually less than 200 (in theory anything from 2 to 200). It can also change from one run to the next, which makes the bug hard to reproduce. I simulated 5 runs with random switching between the two processes and got 109, 117, 118, 111, 120, never 200. The part of the code that touches the shared variable is the critical section, and only one process should be inside it at a time (mutual exclusion).

2.2 Suggested mechanism: a mutex

I'd use a mutex (mutual exclusion lock). Before entering the critical section, a process must lock the mutex. If the other process already holds it, the caller is blocked until it's unlocked. The lock and unlock operations are atomic (the OS or hardware guarantees they can't be interrupted halfway), so only one process can ever hold it. A mutex fits this problem well because there's exactly one shared resource and the same process that locks it also unlocks it. A binary semaphore initialised to 1 would also work (wait/signal instead of lock/unlock), and so would a monitor, which puts the counter and its operations inside one object that only one process can use at a time.

2.3 Pseudocode

shared counter ← 0
shared mutex   ← new Mutex()          // unlocked at the start

procedure Worker(name)                // run once as P1 and once as P2, at the same time
    for i ← 1 to 100 do
        // ----- entry section -----
        lock(mutex)                   // waits here if the other process holds the lock

        // ----- critical section: only one process at a time -----
        temp    ← counter             // LOAD
        temp    ← temp + 1            // ADD
        counter ← temp                // STORE

        // ----- exit section -----
        unlock(mutex)                 // lets the waiting process in

        // remainder section (code that doesn't touch counter)
    end for
end procedure

start Worker("P1") and Worker("P2") in parallel
wait for both to finish
print counter                         // always 200

The same idea with a semaphore:

shared S ← Semaphore(1)
...  wait(S)      // S: 1 → 0, a second caller blocks while S = 0
     counter ← counter + 1
     signal(S)    // S: 0 → 1, wakes one waiting process

This solution meets the three requirements of a correct critical-section solution. Mutual exclusion: only the holder of the lock can be in the critical section. Progress: when the lock is free, a waiting process gets it straight away. Bounded waiting: each process unlocks after one increment, so the other is never kept waiting forever. When I added the lock to the same 5 simulated runs, every one gave 200, 200, 200, 200, 200. The critical section is kept as small as possible (only the increment), so the two processes still run in parallel the rest of the time.

Part 3: Memory Management

The process uses 5 different pages, but only 3 frames are available. Reference string: 1, 2, 3, 2, 4, 1, 5. A F means a page fault (the page wasn't in memory and had to be loaded), and a ✓ means a hit. The first three references are always faults, because memory starts empty (compulsory misses).

3.1 FIFO (First In, First Out)

When a page has to be replaced, FIFO evicts the page that has been in memory the longest, no matter how recently it was used.

When page 4 is requested, page 1 is the oldest page in memory, so it's evicted. Then page 1 is needed straight away, so it causes another fault and evicts page 2 (now the oldest). Finally, 5 evicts 3.

3.2 LRU (Least Recently Used)

LRU evicts the page that hasn't been used for the longest time, based on the idea that a page used recently will probably be used again soon (locality of reference).

When page 4 is requested, page 1 is the least recently used (page 2 was used one step earlier), so 1 is evicted, the same choice as FIFO. When page 1 comes back, LRU evicts 3 instead of 2, because 2 was used more recently. The pages kept are different, but the number of faults ends up the same.

For this reference string, FIFO and LRU perform the same: 6 page faults each. The string is very short and has almost no repeated use. Only page 2 is referenced twice in a short time, and both algorithms keep it. After that, pages 4, 1 and 5 each appear once in a row, so there's no "recent use" pattern for LRU to take advantage of. Even the Optimal algorithm, which knows the future and is the best possible, only saves one fault (5). So there was very little room to improve.

In general, LRU performs better than FIFO. Real programs have locality: they keep using the same pages (a loop, a function, an array) for a while. LRU keeps those recently used pages, while FIFO may throw out a page that is heavily used just because it was loaded early. FIFO can also suffer from Belady's anomaly, where giving it more frames causes more faults, and LRU never does. The downside of LRU is cost: the system has to record when every page is used (with counters or a stack, or approximately with reference bits as in the Clock algorithm), while FIFO only needs a simple queue.

Part 4: Disk Scheduling

The disk head starts at track 53. Pending requests, in the order they arrived: 98, 183, 37, 122, 14, 124, 65, 67. Head movement for each step = |destination − current position|.

4.2 SSTF (Shortest Seek Time First)

At each step, the head goes to the pending request closest to its current position. From 53, the closest is 65 (12 away), then 67 (2 away). From 67, the closest is 37 (30 away, closer than 98 at 31), then 14. Then it goes back up through 98, 122, 124 and 183: 53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183

4.3 Conclusion

SSTF is much more efficient here: 236 tracks instead of 640, which is 404 tracks or about 63% less head movement. The charts show why. FCFS keeps jumping across the whole disk (98 → 183 → 37 → 122 → 14 → 124), while SSTF handles the nearby requests together and only makes one big trip. Since moving the head (seek time) is the slowest part of a disk access, less movement means faster average response and higher throughput.

SSTF has two weaknesses. It isn't always optimal (here it first goes down to 14 and then has to come all the way back up). More importantly, it can cause starvation: if new requests keep arriving near the head, a request far away, like 183, could wait for a very long time. FCFS is fair and never starves a request, but it's slow. In practice, systems often use SCAN or C-SCAN (the "elevator" algorithms), which keep most of SSTF's efficiency while guaranteeing every request is eventually served.
