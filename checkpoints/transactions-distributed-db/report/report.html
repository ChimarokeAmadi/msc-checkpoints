Part 1: Transaction Management

The scenario

The accounts table starts with three accounts: A (Amira) = 1,000 TND, B (Bilel) = 500 TND and C (Cyrine) = 300 TND. Two transfers start at the same time, and both take money from the same account A:

  • T1: transfer 200 from A to B
  • T2: transfer 300 from A to C

Whatever order they run in, the correct result is A = 500, B = 700, C = 600. The bank's total money must stay at 1800, because a transfer only moves money and never creates it.

1. The concurrency issue: a lost update

A transfer is a read-modify-write: read A's balance, subtract the amount in the application, then write the new balance. If both transactions read A before either one writes, they both start from 1000. T1 writes 800, then T2 writes 700 and overwrites T1's update, as if T1 had never touched account A. This is the lost update problem.

Result: A ended on 700 instead of 500, but B and C still got their money. The bank's total went from 1800 to 2000: 200 TND appeared out of nowhere. MySQL raised no error. Its default isolation level (REPEATABLE-READ) does not stop this pattern when the new value is calculated in the application.

Another issue I tested: the dirty read. If a user viewing balances can read uncommitted data, they might see money that never really moved. While T1 was in progress, a reader at READ UNCOMMITTED saw A = 800. Then T1 rolled back, and the real balance was 1000. At READ COMMITTED or higher, the reader saw 1000, which was correct. So "view balance" must never run at READ UNCOMMITTED.

2. The locking mechanism

There are two kinds of locks:

  • Shared lock (S) for reading: many transactions can hold one at the same time.
  • Exclusive lock (X) for writing: only one transaction can hold it, and it blocks both S and X locks from others.
Lock compatibility
held \ requestedSX
S✔✘ wait
X✘ wait✘ wait
My proposal:
  • Transfers take an exclusive (X) lock on both account rows before reading them, with SELECT … FOR UPDATE. They keep the locks until COMMIT (strict two-phase locking).
  • Viewing a balance only needs a shared (S) lock (SELECT … FOR SHARE), or simply a normal committed read.
  • Accounts are always locked in the same order (smallest id first). Then two opposite transfers (A→B and B→A) can't deadlock each other.
START TRANSACTION;
-- lock both rows, smallest id first
SELECT id, balance FROM accounts WHERE id IN (:from, :to) ORDER BY id FOR UPDATE;
-- (in the app: check that balance(:from) >= :amount, otherwise ROLLBACK)
UPDATE accounts SET balance = balance - :amount WHERE id = :from;
UPDATE accounts SET balance = balance + :amount WHERE id = :to;
COMMIT;   -- releases the locks

Why not shared locks alone? I tried it. Both transactions got an S-lock on A, because S-locks are compatible. Then each one needed to upgrade to an X-lock to write, and each was waiting for the other. MySQL detected the deadlock (error 1213 ER_LOCK_DEADLOCK) and rolled T2 back. The result was correct after the retry, but only because MySQL broke the deadlock. For read-modify-write, the lock has to be exclusive from the start.

I would use pessimistic locking for transfers, for four reasons:
  • Conflict is part of the scenario. Two users are hitting the same account. With optimistic locking, one of them is guaranteed to fail and redo the work, and under heavy load this could keep happening.
  • It's money. The cost of getting it wrong is very high. Pessimistic locking makes it impossible for two transfers to work on the same balance at the same time. Optimistic locking only works if every piece of code remembers the version check.
  • Transfers are short: two rows, a few milliseconds. The locks are held very briefly, so waiting is cheap (here it was 311 ms, only because I paused T1 on purpose).
  • The user experience is simpler. T2 just waits a moment. It doesn't get a "please try again" error.
I'd keep optimistic locking for low-conflict data, like a customer updating their address.

4. Order of operations: is the schedule safe?

Schedule 1 (no locking) is shown above. Written in short form, it is r1(A) r2(A) w1(A) w2(A). It is not conflict-serializable: r1(A) comes before w2(A), which gives an edge T1 → T2, and r2(A) comes before w1(A), which gives an edge T2 → T1. The precedence graph has a cycle, so no serial order gives the same result. Not safe.

Schedule 2 uses my exclusive locks. T2's lock request waits, so it reads A only after T1 commits. The schedule becomes equivalent to the serial order T1 → T2. Safe.

Part 2: Distributed Database Planning

The bank has three branches: Tunis, Sousse and Sfax. In my demo, each branch is its own MySQL database (a "site"): bank_tunis, bank_sousse and bank_sfax. The login data goes in bank_auth. I started from a central database with 12 customers, 18 accounts and 6,000 transactions, and split it.

1. Horizontal fragmentation of Customers by branch

Each customer belongs to a home branch, the branch where they opened their account. I split the rows with one predicate per branch. Each fragment is a selection of the Customers table:

Customers_Tunis  = σ branch = 'Tunis'  (Customers)
Customers_Sousse = σ branch = 'Sousse' (Customers)
Customers_Sfax   = σ branch = 'Sfax'   (Customers)

CREATE TABLE bank_tunis.customers AS
  SELECT customer_id, full_name, branch, phone, address
  FROM bank_central.customers
  WHERE branch = 'Tunis';

Each fragment is stored at its own branch, so most work (opening accounts, deposits, local customers asking for their balance) uses only local data, with no network trip. I also added CHECK (branch = 'Tunis') to the Tunis fragment. When I tried to insert a Sfax customer there, MySQL refused (ER_CHECK_CONSTRAINT_VIOLATED).

2. Vertical fragmentation: the login information

I would move the login information (email, password_hash, last_login) into its own table, customer_login. It keeps the key customer_id so the two parts can be joined back.
CREATE TABLE bank_auth.customer_login AS
  SELECT customer_id, email, password_hash, last_login
  FROM bank_central.customers;
  • Security: credentials are the most sensitive data. In a separate table (here, a separate database), they can have stricter permissions and encryption, and branch staff who look up customer profiles never touch them.
  • Different use: login data is read on every login, from anywhere (mobile app, any branch). The profile (address, phone) is read much less often, and mostly at the home branch.
  • Not tied to a branch: a customer should be able to log in from any city, so this part is treated differently (see replication below).

Branch sites keep: customer_id, full_name, branch, phone, address. bank_auth.customer_login keeps: customer_id, email, password_hash, last_login. Joining the two on customer_id gave back the original table exactly: ✔ yes (a lossless vertical split).

3. What should be replicated to all branches?

DataReplicate to all 3 branches?Why
Customer info
(a directory: id, name, home branch; and the login data)		Yes It's small, it's read all the time (identifying a customer, logging in), and it rarely changes. With a copy everywhere, any branch can serve any customer, and it knows where that customer's accounts live. The rare updates go to one primary copy and are sent to the others. A few seconds of delay is fine for a name or a phone number.
Account balancesNo Balances change with every transfer and must always be exact. If all three branches had a copy, every transfer would have to update three sites at once (with two-phase commit), which is slow. And if a network link went down, two branches could accept withdrawals from different copies, so money could be spent twice. I keep one primary copy at the home branch (plus a backup standby for failures, not used for writes).
Transaction historyNo (not to every branch) It's by far the largest data set (6,000 rows for 12 customers in my demo) and it grows forever. Each customer's history is mostly needed at their home branch. It's append-only, so I'd only copy it asynchronously to one central backup/audit site, not to every branch.

Here's how the directory is used in the demo. Amira Ben Salah, a Tunis customer, walks into the Sfax branch. The local copy of customer_directory (12 rows at every site) finds her straight away and says her home branch is Tunis. The balance query is then sent to bank_tunis (7,173.79 TND), the only place the real balance is stored.

4. Static or dynamic allocation for transaction history?

Static allocation. Each transaction is stored at its account's home branch, decided once when the system is designed.
  • The access pattern is predictable. History is almost always read by the account owner's branch. We know this in advance, so there's nothing to gain from moving data around automatically.
  • The data is append-only and huge. Old transactions are never updated. Dynamic allocation would keep moving large amounts of rows between cities, using network bandwidth and creating risk for no real benefit.
  • It's simpler and easier to audit. Everyone (the queries, the auditors, the backup plan) knows exactly where a transaction lives.

Dynamic allocation would only make sense if usage changed a lot, for example if many customers moved between cities. Even then, I'd handle it with an occasional planned move of that customer's fragment rather than automatic, continuous reallocation.

What I learned

The biggest surprise was that the lost update happened silently. MySQL gave no error or warning, and the bank simply ended up with 200 TND that shouldn't exist. Transactions alone don't protect you. You have to choose the right locks (here, an exclusive lock taken before reading), or check a version number. I also learned that shared locks can make things worse for read-modify-write, because they lead to deadlocks.

For the distributed part, the main idea is to keep data where it's used: fragment customers, accounts and history by branch. Then replicate only what is small, read often and rarely changed, which is the customer directory and login data. Balances need one exact copy, and history is too big and too local to copy everywhere.
